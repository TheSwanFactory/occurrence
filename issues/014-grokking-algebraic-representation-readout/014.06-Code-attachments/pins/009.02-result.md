## 6. Arm C — construction and the automorphism rejection proof

### 6.1 Why permuting codes is permuting edges

Inside a habitat an SFP code word **is** a K4 edge. There are six code words and
six edges, and the correspondence is the identity of the construction, not an
analogy. So permuting the six codes is *exactly* permuting the six edges, and the
question "is this scramble structure-destroying?" becomes a finite question about
`S6` acting on `E(K4)`.

```text
6! = 720   total permutations of the six codes
      24   induced by K4 vertex automorphisms / affine AGL(2,2)
     696   not structure preserving
```

### 6.2 The draw

14 independent digest-pinned per-habitat permutations, one per habitat, drawn by

```text
sha256("009/task6/arm-c-scramble/v1|<habitat>") % 696
```

from the **lexicographically sorted** pool of the 696 non-induced permutations.
All 14 satisfy `groups.is_structure_preserving == False`. The pool is filtered
before the draw, so rejection is a property of the construction rather than a
post-hoc filter on a sample.

### 6.3 Two traps, recorded as avoided

**Trap 1 — permuting the three nonzero `pp` values is a symmetry, not a
scramble.** All 6 such permutations lie in `GL(2,2) ≅ S3` and all 6 preserve
`d3 = d1 XOR d2`. A "scramble" built that way would be a relabeling and would
have shown Arm-D behaviour while being reported as destruction. Never used.

**Trap 2 — matching-partition preservation is necessary but not sufficient.**

```text
720  permutations of the six edges
 48  preserve the matching partition
 24  are actually induced
```

So a partition-preservation test would admit 24 impostors. Rejection therefore
tested membership in the 24-element induced class only.

This is not hypothetical, and the data shows it:

```text
2 of the 14 accepted scrambles  (P=4, delta=-1)  and  (P=7, delta=+1)
  preserve the matching partition
  admission disagreements        0
  forced thirds lost         24 / 24     (all of them)
```

A non-induced but partition-preserving permutation carries a K4 **star** — a
certified block — onto a K4 **triangle**. Admission survives because the pair
still shares *a* block; forcing dies because the third Event of the image is a
different Event. Had trap 2 not been closed, those two habitats would have looked
like harmless relabelings while silently destroying the forcing relation.

### 6.4 Marginal match, and what it buys

Arm C reuses the same 84 valid code words, so its marginals match Arm B
**exactly**:

```text
per-unit counts   [84, 84, 24x7, 42x4, 56x3]
per-field multisets   identical
```

Bit widths, habitat sizes and field marginals are held identical between B and C.
That is what makes the `B - C` gap attributable to relational alignment rather
than to code capacity.

### 6.5 What C destroys

```text
relation destroyed in         14 / 14 habitats
global admission preserved  6936 / 7056
global forced third            66 / 336
```

```text
architectures                     1, shared by A/B/C/D
```

### 12.1 The one repair, and why it was motivated before it was run

`mask_held_out_candidates=True`. The motivation is a diagnosed defect, not a
tuning intuition, and `harness.py` diagnosed it:

On a held-out-habitat fold the correct forced third is *itself* a held-out Event.
It is scored as a candidate during training but is never the right answer, so
cross-entropy actively suppresses exactly the slots the test set needs. The
signature is unmistakable:

```text
train accuracy at ceiling   0.944
forced third at floor       0.028
errors that were a wrong Event inside the correct habitat   2.5%
```

If forcing were failing because the model could not localize the habitat, that
last number would be large. At 2.5% it is not: the model is not choosing the
wrong Event in the right habitat, it is refusing the right region entirely.

### 12.2 Outcome — tested and insufficient

```text
B_sfp forced third   0.0335  ->  0.0900
```

It moves, and it stays at the floor. No qualitative conclusion changes. The
repair also does not compromise the experiment:

```text
alters fold membership          no
alters labels or ground truth   no
adds per-Event output identity  no
leaks any SFP rule              no
```

**No second repair was attempted.** The rule permits one, and searching for
another after seeing these results would be tuning, not repair.

The commissioned task is **admit AND force**. Forcing is unsolved by every
representation: max forced-third accuracy over all arms is `0.0335` in the
primary block while both nonlearned oracles score `1.0`. **No arm demonstrates
held-out relational generalization of the certified relation as a whole.** That
is disposition E.

But E's clause "representation comparison is unresolved" overstates the
uncertainty relative to what was measured. The **admission half is cleanly

throughout. Per hypothesis:

| `H_equiv` | **SUPPORTED on admission** |

| `H_exec` | established upstream by `021.05`; **not retested** |

- **`H_equiv`.** D matches B under `GL(3,2)` + affine `AGL(2,2)` + a global `S`

- **`H_realization`.** Native realization did not merely fail to add advantage —
  it sat at **chance** (`0.5048`) on admission while the compact code reached
  `0.8820`. The task framed this as "does native realization help?"; the answer

## 14. Recommendation on the opaque-token discovery stage

**Not warranted yet.**

Arm B is handed the exact certified code — the code that `ExactSFPCircuit` proves
sufficient at `1.0` — and still cannot name the held-out forced third. Hiding
that code behind opaque tokens produces a strictly harder version of an already
failing task. Whatever it returned, it could not discriminate: a floor result
under opaque tokens is consistent both with "discovery is hard" and with "forcing
is hard", and this turn shows forcing is already hard with the code supplied.

The prerequisite is to **close the forcing gap under a supplied code first**. The
concrete next step: keep Arm B and the frozen LOHO folds exactly as they are, and
attack forcing directly — the section 12.1 diagnosis (held-out target suppression
with only 2.5% of errors inside the correct habitat) says the failure is in how
held-out candidate slots are treated, not in habitat localization. Only once some
arm names held-out forced thirds materially above floor does an opaque-token
discovery stage become a test that can fail.
