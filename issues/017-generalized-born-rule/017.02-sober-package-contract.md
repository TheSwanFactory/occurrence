# 017.02 — Define the SOBER package contract

- **Sequence:** 2 of 5
- **Target:** successor SOBER package/repository
- **Status:** dispatch after 017.01 API shape is fixed
- **Issue effect:** successor work; not an Issue 017 acceptance criterion

## Objective

Create the public contract for **SOBER — System-One Born Effect Resolver** as a computational layer that may consume `topographo` without becoming part of `topographo`.

The dependency direction must be one-way:

```text
topographo  <-  sober
```

`topographo` owns certified mathematical and OT primitives. `sober` owns the computational state/effect/test interface. `topographo` must not import `sober`.

## Minimum public semantics

The package contract should express:

```text
ResolveEffect : State x Effect -> Probability
ResolveTest   : State x Test   -> Distribution
```

with explicit representations or protocols for:

```text
State
Effect
Test
Probability
Distribution
Resolver
```

A test is a typed exhaustive family of effects. Resolution ends at a probability or distribution. Sampling, argmax, thresholding, narration, decisions, actions, and Event enactment are downstream policy and are not resolver semantics.

## Boundary contracts

Keep these representation problems outside the resolver core:

```text
Prepare   : Datum -> State
Interpret : TypedQuestion / OutputType -> Effect / Test
```

Do not make state-driven effect generation, language encoding, or autonomous decision-making prerequisites for the first package release.

## Packaging decision

Prefer a separate `sober` distribution/repository if SOBER is intended to support more than the OT/sedenion backend. If launch constraints require a temporary monorepo location, record that as transitional and preserve the same dependency fence.

Before publication, settle:

1. package and import names;
2. license and ownership metadata;
3. supported Python versions;
4. whether `topographo` is required or an optional backend dependency;
5. stability guarantees for the first public API;
6. the exact scientific claims permitted in the README and campaign.

## Done when

- a package charter and public API are written;
- dependency direction is explicit and mechanically enforceable;
- the resolver boundary excludes preparation, interpretation, and decision policy;
- the README distinguishes certified behavior from research direction;
- the initial release scope is small enough to implement and demonstrate this week.
